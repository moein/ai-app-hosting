# 15 — File Storage: Requirements

Every app gets its own R2 bucket, the same shape as its own D1 database (spec 09, RUN-2.1): provisioned automatically, injected as a binding the app's code uses directly, never declared by the app in `wrangler.jsonc`. This lets an AI-built app store uploads (images, documents, exports) without the user ever choosing or configuring a storage provider. Usage is tracked per spec 13 so it can be shown and priced like everything else.

## Stories & acceptance criteria

### FILE-1 — Provisioning
As a user, I want my app able to store files from the moment it's created, so that the AI can build upload features without asking me to set anything up.

- **FILE-1.1** WHEN an app is provisioned THE SYSTEM SHALL create an R2 bucket named `app-<slug>-<environment>` and store its name in `apps.r2_bucket_name`.
- **FILE-1.2** THE SYSTEM SHALL make bucket provisioning idempotent (an existing bucket of that name counts as success), following the same step shape as `d1` in `provisionSteps` (spec 03, APP-2.3).
- **FILE-1.3** IF bucket creation fails after the workflow's retries THEN provisioning SHALL fail with the same `provisioning_failed` handling as any other step (APP-2.5).
- **FILE-1.4** `delete_app` SHALL NOT delete the app's bucket (APP-4: only the Worker is removed, mirroring D1 and the email identity). The dev-only e2e purge job is the one exception, exactly as it already is for D1 (E2E-4.2, amended by this spec to also empty and delete the bucket).

### FILE-2 — Runtime binding
As an AI client, I want a storage binding just like the database binding, so that app code can read and write files without extra setup.

- **FILE-2.1** THE SYSTEM SHALL add `FILES` (an `r2_bucket` binding to the app's own bucket) to the bindings every deployed app script gets (RUN-2.1 is amended to include it).
- **FILE-2.2** `FILES` SHALL be a reserved binding name exactly like `DB`, `ASSETS` and `EMAIL` (CON-2.5, amended by this spec): THE SYSTEM SHALL reject a `wrangler.jsonc` that declares an `r2_buckets` key (unsupported key, same as any other unlisted key, CON-3.3) or a `vars` entry named `FILES` (CON-R10/CON-R12).
- **FILE-2.3** THE SYSTEM SHALL document in the platform guide that `env.FILES` is a standard Workers `R2Bucket` (`put`, `get`, `delete`, `list`, `head`) and that apps serve file contents by proxying `env.FILES.get(key)` through their own Hono routes — buckets are never public.

### FILE-3 — Inspecting stored files
As an AI client, I want to see what's in the app's bucket, so that I can debug an upload feature without writing throwaway inspection code.

- **FILE-3.1** WHEN `list_storage_objects({ app, prefix?, cursor? })` is called THE SYSTEM SHALL return up to `MAX_STORAGE_LIST_KEYS` objects (`key`, `size`, `uploaded_at`, `etag`) under `prefix` (default: all), plus a `cursor` for the next page when more exist.
- **FILE-3.2** THE SYSTEM SHALL NOT return object contents through MCP (objects can be arbitrary binary data and are the app's own to serve); reading content is the app's job.
- **FILE-3.3** THE SYSTEM SHALL require the app to be ready (`resolveApp` with `requireReady`, same as `list_files`/`query_database`) before listing its bucket: an unknown app → `NOT_FOUND`; one still provisioning or failed → `APP_NOT_READY`. Once `provisioning` is `ready` the `r2` step has already succeeded, so the bucket always exists by the time this runs.

## Non-functional requirements

- No object size limit imposed by the platform beyond what R2 itself supports; large uploads use R2's multipart API from the app's own code.
- No per-app storage quota in v1 — usage is tracked and priced (spec 13), not capped, matching D1.

## Out of scope

- Public bucket URLs or a platform-managed CDN in front of R2 (apps proxy their own access).
- Presigned upload/download URLs generated by an MCP tool.
- Object versioning, lifecycle rules, or cross-app/cross-org sharing.
- Reading or writing object contents through MCP.
